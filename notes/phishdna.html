~/phishdna

Some notes from building PhishDNA, my final project for CCAI9028 – The Age of Big Data.

PhishDNA started as a course project, but it ended up changing how I think about machine learning. Before this project, I thought choosing the right model was the difficult part. Instead, most of my time was spent understanding the data and figuring out why the model behaved the way it did.

Why I built it

Around Feb 2026, I came across a Threads post showing a phishing website pretending to be HSBC.

The website looked very convincing. Most of the comments reminded the original poster not to enter any personal information. The poster replied,

"Of course I won't. As long as I do not type anything in, I am safe."

I shared the post on my own account, and a few friends replied saying they had always thought the same thing.

That surprised me.

Many people think phishing websites only become dangerous after they enter their password or credit card details. In reality, simply visiting a malicious website can already expose users to attacks such as drive-by downloads or browser-based exploits.

That made me wonder whether it was possible to warn users before the webpage even loaded.

Instead of analysing the webpage itself — which means interacting with potentially malicious content — I wanted to see how much information could be extracted from the URL alone. If the URL already looked suspicious, maybe users could be warned before opening the page.

That became the starting point of PhishDNA.

The original idea

My original plan was actually more ambitious than the final project.

I wanted the browser extension to intercept a website before the browser sent the request. If the predicted risk score was high enough, the extension would block the page completely and show a warning instead.

As I started building it, I realized there were a lot more things to consider than I had expected. Intercepting browser requests properly would take much more time than I had left for the course.

In the end, I simplified the project.

Instead of blocking websites, the extension analyses the current URL, predicts a phishing risk score, and explains why the URL might be suspicious. It still demonstrates the complete detection pipeline while keeping the project manageable within one semester.

Everything looked perfect… at first

The first model looked really promising.

I trained a Random Forest model and evaluated it using the test dataset.

Accuracy, precision, and recall were all above 90%.

At that point, I honestly thought I was almost done.

Then I started testing websites I actually visit every day.

  • Google
  • GitHub
  • HKU
  • Government websites

Some of them were classified as phishing.

That is when I realized something I had not expected.

A model can perform really well on a test dataset and still perform terribly in the real world.

That was probably the biggest surprise of the entire project.

I spent a week fixing the wrong thing

My first reaction was to assume the model needed more tuning.

So I started changing everything.

  • I adjusted the scoring logic.
  • I replaced URL length with effective URL length (only counting the length of FQDN instead of the full URL).
  • I limited the contribution of certain features so that no single feature could dominate the prediction.
  • I kept retraining the model, hoping the false positives would disappear.

They did not.

It took me a while to realize I was solving the wrong problem.

The dataset was cheating

Eventually, I stopped looking at the model and started looking at the data.

That is when everything suddenly made sense.

The legitimate URLs in my dataset were mostly simple domain names like:

google.com
apple.com
github.com

Meanwhile, almost every phishing sample was an extremely long URL full of random-looking strings.

The model was not really learning phishing patterns.

It had simply learned that long URLs usually meant phishing.

Technically, the model achieved high accuracy.

In reality, it had found a shortcut.

I remember opening the feature importance graph and seeing URL length taking up most of the importance score. That was the moment I realized something was not right.

Replacing the dataset probably improved the project more than all the tuning I had done before.

I ended up rebuilding the training pipeline using much larger public datasets, including the Global Phishing Database, the Tranco Top Sites list, and a Hong Kong-specific dataset containing legitimate government, banking, and education domains.

Teaching the model what humans notice

Once the dataset became more balanced, I started thinking about something else.

There are URLs that most people would immediately find suspicious.

For example:

whatsd-app.com
paypa1.com
apple-security-check.top

A machine learning model does not naturally understand why those look suspicious.

So I started adding features that capture things humans notice almost instinctively.

  • Does it look like a typo of an existing website?
  • Is it using a suspicious top-level domain?
  • Does it contain a long string of random-looking characters?

Instead of relying on one feature, the model gradually learned to combine many small signals together.

That made the predictions much more reliable than simply checking whether a URL was long.

Building the extension

Once I was happy with the model, I started working on the Chrome extension.

The extension reads the current URL, sends it to a FastAPI backend, receives the prediction, and displays the phishing risk score together with an explanation.

Most of the implementation went quite smoothly, but I ran into one bug that confused me for a while.

The extension sometimes produced different results from the Python version.

The same URL could receive two different risk scores.

After a few hours of debugging, I realized the extension was not applying my hard override rules.

For example, trusted government domains should always receive a risk score of zero, but the extension was still sending them through the normal scoring pipeline.

Once I fixed that, both versions finally produced the same results.

Looking back

Before this project, I thought the hardest part of machine learning would be choosing the right model.

Now I think that is probably one of the easier parts.

Most of my time was spent understanding the data, figuring out why the model behaved strangely, and checking whether the results actually made sense.

Another thing I learned is that evaluation metrics do not tell the whole story. A model with high accuracy is not necessarily useful if it fails on real websites.

Finally, I realized that machine learning alone is not enough for phishing detection.

The final version of PhishDNA combines machine learning with rule-based checks because some phishing techniques are much easier to describe with explicit rules than expecting the model to learn everything from data.

If I were to rebuild PhishDNA today, I would probably spend less time tuning the algorithm and more time understanding the dataset first.
