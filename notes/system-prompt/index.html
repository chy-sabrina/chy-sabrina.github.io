[thoughts] system prompt

Quick disclaimer: Notes tagged with [thoughts] are just my personal take. They are not meant to be perfectly written, or necessarily correct. I may have misunderstood something.

Why I started thinking about this

I have been working on system prompt-related stuff quite a bit this month. I also got to look through the system prompts of three real chatbot projects.

That was the first time I had enough real examples to compare with what I had always imagined a system prompt would look like.

What I thought a system prompt was

Before my internship, I had a pretty clear picture in my head.

I thought a system prompt would be one big block of text that tells the chatbot basically everything: what it is, what it should do, what it should not do, how it should respond, and all the security rules.

Basically:

  • long
  • detailed
  • very structured
  • full of rules
  • probably a little terrifying to read

I think part of this came from reading leaked system prompts. They are often shown as one huge block containing the model's identity, instructions, restrictions, formatting rules, and everything else.

What I saw in real projects

Real projects were not really like that.

The biggest difference was that there was not just one giant prompt doing everything.

The application looked more like this:

> pipeline

User
↓
PII scrubber
↓
Input filter
↓
RAG
↓
LLM
↓
Output filter
↓
PII scrubber / truth checker
↓
Output

And some of those components (e.g., input filter, output filter and truth checker) are also LLM, and have their own prompts too.

For example, the system prompt of the truth checker is something like:
Evaluate the alignment between the provided answer and the retrieval context in response. If the answer is entirely based on the provided **Retrieval Context**, return "true"; otherwise, return "false".
...
The task is to determine whether the information within the retrieval context adequately supports the provided answer.
...
# Output Format
Output should be a single word—either "true" or "false", reflecting whether the answer is supported by the retrieval context or not.

So instead of thinking about "system prompt" as one thing, I started thinking about a bunch of smaller prompts sitting in different parts of the application.

There was business logic in there too

Another thing that surprised me was seeing business logic inside the system prompt.

For example, a prompt might tell the model to classify a user's request into different categories and then send them to a different chatbot or workflow.

I did not expect that.

I always thought of a system prompt as something that mainly tells the model how to behave. I did not really think of it as part of the application's decision-making logic.

It also made me wonder whether some of this logic should be somewhere else. If something is important business logic, relying on the model to interpret it correctly feels a little strange.

So where is the security stuff?

This was the part that surprised me the most.

The system prompts I saw did not always contain that much security-related stuff.

Things I expected to see in the prompt, like content filtering, jailbreak prevention, or indirect prompt injection protection, were often handled by guardrails instead.

There was also normal code around the LLM doing input and output sanitization, such as converting SQL commands or HTML tags into plain text.

That made sense to me. If something can be checked deterministically with code, why ask an LLM to do it?

So what is the system prompt actually for?

From the projects I looked at, my current guess is that the system prompt is mostly there to give the model its role and tell it what it is supposed to do.

Things like:

  • what the chatbot is
  • what its job is
  • how it should respond
  • what format to use
  • some general rules it should follow

There are still some security-related instructions in there. For example, don't disclose internal information or don't reveal certain internal data.

But from what I saw, they are also implemented using guardrail. The system prompt did not seem to be the main security layer.

Which made me wonder...

How important is the system prompt actually from a security perspective?

Before this, I probably would have said it was extremely important. It is the model's highest-level instruction, so it feels like it should be one of the main security controls.

After looking at actual applications, I am less sure.

The security seems to come from the whole setup around the model: input filtering, output filtering, guardrails, PII scrubber, validation, RAG controls, and scripts.

The system prompt is still important because it controls a lot of the model's behavior. I just don't think it should be treated as the security boundary by itself.

My current thought

I am probably still figuring this out.

Before my internship, I mostly thought of a system prompt as one giant piece of text. Now I think of it as one part of a much bigger system.

And maybe that is the more useful way to look at it: the system prompt matters, but it should not have to do everything.
